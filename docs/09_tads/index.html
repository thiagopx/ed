Módulos e tipos abstratos de dados

Tipo abstrato de dados

Estas são as notas da aula sobre abstração, módulos e tipos abstratos de dados: como dividir um programa em arquivos de interface e de implementação, e como um TAD esconde a forma concreta de um tipo atrás de um conjunto de operações. Os três exemplos abaixo são projetos com vários arquivos e Makefile.

Antes do capítulo: o que é abstrair

Abstrair é deixar de lado os detalhes que não importam para aquilo que se quer fazer. Você dirige um carro sem saber como o motor queima combustível, e usa um telefone sem conhecer a rede que transporta a sua voz. Nos dois casos você depende de um conjunto de operações bem definido (girar a chave, discar um número) e não da maneira como cada uma delas é realizada por dentro.

Em programação, a abstração tem o mesmo papel. Um programa grande tem milhares de linhas, e muitas pessoas trabalham nele. Se cada parte precisasse conhecer os detalhes internos de todas as outras, qualquer mudança pequena se espalharia pelo código inteiro, e ninguém conseguiria raciocinar sobre uma parte sem entender o resto. Abstrair permite usar uma parte confiando no que ela promete, e não no modo como ela faz o que promete.

Abstração de dados

Quando a abstração recai sobre um tipo de dado, falamos em abstração de dados. A pergunta muda: deixamos de perguntar "como este tipo guarda as informações?" e passamos a perguntar "o que este tipo faz com elas?". Para um ponto no plano, o que importa a quem usa é conseguir calcular a distância até outro ponto. Se as coordenadas ficam em dois campos separados ou num vetor de dois elementos, isso é um detalhe.

Separamos, então, duas coisas. O que o tipo faz são as suas operações, o contrato que ele cumpre. Como ele faz é a estrutura interna e o código que implementa cada operação. Quem escreve o programa cliente depende apenas da primeira. Quem escreve o tipo cuida da segunda, e pode mudá-la sem alterar o contrato, sem que o cliente precise saber disso.

Tipo abstrato de dados

Esta seção trata da técnica de definir um tipo estruturado junto com as operações que o manipulam, escondendo a sua implementação. Começamos pelo mecanismo que a linguagem C oferece para isso: os módulos.

Módulos e compilação em separado

Um programa em C pode ser dividido em vários arquivos-fonte, com extensão .c. Quando um arquivo reúne funções que formam uma parte coesa do programa, ele é um módulo. Cada módulo é compilado separadamente, e o resultado é um arquivo objeto (.o). Depois, o ligador (linker) junta os objetos num único executável. É nessa etapa que o código das funções da biblioteca padrão entra no programa. Mesmo um programa de um único arquivo passa pela ligação.

A divisão em módulos se justifica quando o programa cresce. Uma tarefa grande vira tarefas menores, que são mais fáceis de implementar e de testar. Além disso, um módulo bem feito pode ser reaproveitado em outros programas sem copiar código.

Programa cliente e módulo: quem usa e quem oferece

Em todo módulo há dois papéis. O programa cliente, que tem o main e o código que o sustenta, usa o que o módulo oferece. O módulo oferece funções e tipos, e esconde como eles são feitos. O cliente conhece o contrato. O módulo guarda a implementação.

O contrato fica no arquivo de interface, o cabeçalho (.h). Ele contém os protótipos das funções exportadas, os tipos que o cliente precisa conhecer e a documentação de cada função. A implementação fica no arquivo .c, que inclui o próprio cabeçalho e define as funções. O cliente inclui o cabeçalho e não precisa abrir o .c para usar o módulo.

O projeto 01_modules mostra essa separação. O main.c inclui apenas my_string.h e chama my_strlen, my_strcpy, my_strcat e my_strcmp. Ele não sabe se essas funções usam um laço, recursão ou outra técnica. As definições estão em my_string.c. Se o main.c chamasse uma função que o cabeçalho não declara, o compilador reclamaria. Se o cabeçalho declarasse uma função que ninguém define, o erro só apareceria na ligação, porque o linker não encontra o código correspondente.

O cabeçalho deve ter guardas de inclusão (#ifndef, #define e #endif), para que uma inclusão repetida não redefina nada. Cabeçalhos do projeto são incluídos com aspas, como em #include "my_string.h". Cabeçalhos da biblioteca padrão usam <...>.

Tipo abstrato de dados

Quando um módulo define um novo tipo e o conjunto de operações que o manipula, ele representa um tipo abstrato de dados (TAD). "Abstrato" quer dizer que o TAD é descrito pela finalidade do tipo e das suas operações, e não pela forma como foi implementado.

O mecanismo central é o encapsulamento. No cabeçalho, a struct só é declarada, por exemplo com typedef struct circle Circle;. A definição struct circle { ... } fica no arquivo .c. Quem usa o TAD manipula apenas ponteiros, como Circle *, e chama as funções exportadas. Como não enxerga os campos, o cliente não pode depender deles, e a implementação pode mudar sem que o código cliente mude.

Em geral, um TAD oferece uma operação de criação, que aloca e inicializa o objeto e devolve um ponteiro; uma de liberação, que desaloca o que foi criado; operações de acesso e atribuição; e operações de consulta ou cálculo. Quando uma operação recebe outro tipo, o cabeçalho do TAD inclui o cabeçalho desse tipo, como o círculo faz com o ponto.

Para que vários TADs possam ser usados no mesmo programa, as funções exportadas levam o nome do tipo como prefixo (create_point, free_point, create_circle). Assim, funções de tipos diferentes não colidem. Funções auxiliares do módulo são declaradas como static e ficam visíveis só no arquivo que as define. Variáveis globais exportadas devem ser evitadas, porque elas quebram o encapsulamento.

O material de referência usa outra convenção de nomes, com prefixos curtos como pto_cria e circ_cria. Os exemplos desta página usam inglês no código, com create_point e create_circle. A estrutura é a mesma nos dois casos.

Exemplo 1: TAD Ponto

O TAD Ponto representa um ponto no plano. O material de referência define cinco operações: cria, libera, acessa, atribui e distancia. O projeto 02_circle implementa três delas: create_point (cria), free_point (libera) e euclidean_distance (distância). A struct point2d é definida só em point2d.c, e o cliente recebe apenas Point2D *.

Operações conceituais. O TAD Ponto também prevê acessa (devolver as coordenadas) e atribui (trocar as coordenadas). O exemplo não as implementa. No projeto não existe função para ler nem para alterar x e y depois da criação. Essas operações entram aqui para completar o conceito do TAD, mas não há código correspondente para executar.

Exemplo 2: TAD Círculo

O TAD Círculo usa o TAD Ponto para representar o centro. O material de referência prevê as operações cria, libera, area e interior. O projeto implementa create_circle, free_circle e is_point_inside_circle.

create_circle cria o centro com create_point e guarda o ponteiro na struct circle. free_circle libera primeiro o centro e depois o próprio círculo. is_point_inside_circle calcula a distância entre o ponto e o centro e a compara com o raio: se a distância for menor, o ponto está dentro.

A função de consulta recebe um Point2D *, por isso circle.h inclui point2d.h. Um programa que usa o círculo também precisa do ponto, e por isso o test_circle.c inclui os dois cabeçalhos.

Operação conceitual. O TAD Círculo também prevê area, o cálculo da área do círculo. O exemplo não a implementa: não há função de área no projeto. Ela aparece aqui apenas para completar o conceito do TAD.

Exemplo 3: TAD Matriz

Este exemplo mostra o encapsulamento de forma mais completa: a mesma interface pode ser implementada de maneiras diferentes. A matriz tem m linhas e n colunas, com dimensões escolhidas em tempo de execução. As seis operações do material de referência estão implementadas: matrix_create (cria), matrix_free (libera), matrix_get (acessa), matrix_set (atribui), matrix_rows (linhas) e matrix_cols (colunas).

O projeto usa um vetor simples. A struct guarda o número de linhas, o número de colunas e um ponteiro float *data para um bloco contíguo de m × n elementos. O elemento (i, j) fica na posição i * cols + j. Essa é uma escolha interna de matrix.c. O material de referência também descreve a estratégia com vetor de ponteiros (float **), em que cada linha é alocada separadamente. A interface é a mesma nas duas estratégias.

O test_matrix.c não toca nos campos da struct. Ele preenche, percorre e imprime a matriz usando só as funções de matrix.h. Por isso, trocar o vetor simples por vetor de ponteiros não exige mudança nesse arquivo. Muda apenas o conteúdo de matrix.c.

Módulo my_string

#include "my_string.h"
#include <stdio.h>

int main()
{
    char str1[50] = "Hello, ";
    char str2[] = "World!";

    // my_strlen
    int length = my_strlen(str1);
    printf("Length of str1: %d\n", length);

    // my_strcpy
    my_strcpy(str1, str2);
    printf("Copied string: %s\n", str1);

    // my_strcat
    char str3[50] = "Hello, ";
    my_strcat(str3, str2);
    printf("Concatenated string: %s\n", str3);

    // my_strcmp
    int result = my_strcmp("apple", "banana");
    if (result == 0)
        printf("Strings are equal\n");
    else if (result < 0)
        printf("str1 is less than str2 (result = %d)\n", result);
    else
        printf("str1 is greater than str2 (result = %d)\n", result);

    return 0;
}

Como funciona o projeto

O projeto tem dois módulos. my_string.h é a interface: declara as quatro funções exportadas (my_strlen, my_strcpy, my_strcat, my_strcmp) e tem guarda de inclusão. my_string.c é a implementação, compilada separadamente. main.c inclui só o header, com aspas, e não conhece o corpo das funções.

O Makefile compila cada .c em um .o com gcc -Wall -c e depois liga os dois objetos num único executável. make run faz a compilação e roda o programa. Qualquer cliente de my_string.h poderia reutilizar my_string.c sem copiá-lo.

#include "my_string.h"

// Function to calculate the length of a string (analogous to strlen)
int my_strlen(const char *str)
{
    int length = 0;

    while (str[length] != '\0')
        length++;

    return length;
}

// Function to copy one string to another (analogous to strcpy)
void my_strcpy(char *dest, const char *src)
{
    int i = 0;

    while (src[i] != '\0')
    {
        dest[i] = src[i];
        i++;
    }

    dest[i] = '\0'; // Null-terminate the destination string
}

// Function to concatenate two strings (analogous to strcat)
void my_strcat(char *dest, const char *src)
{
    int dest_len = my_strlen(dest);
    int i = 0;

    while (src[i] != '\0')
    {
        dest[dest_len + i] = src[i];
        i++;
    }

    dest[dest_len + i] = '\0'; // Null-terminate the concatenated string
}

// Function to compare two strings (analogous to strcmp)
int my_strcmp(const char *str1, const char *str2)
{
    int i;

    for (i = 0; str1[i] != '\0' && str2[i] != '\0'; ++i)
    {
        int d = str1[i] - str2[i];

        if (d != 0)
            return d;
    }

    return (str1[i] - str2[i]);
}
Pergunta de checagem

O que aconteceria se o executável fosse gerado só com main.o, sem my_string.o?

  • AA ligação falharia com erro de referência não resolvida para my_strlen e as demais funções.
  • BO programa compilaria e rodaria, usando as funções de string.h da biblioteca padrão.
  • CO erro apareceria na compilação de main.c, porque o header não tem a implementação.
  • DO programa rodaria, mas sem a linha de printf que usa my_strlen.

Certo! Na ligação, o linker não encontra o código de my_strlen, my_strcpy, my_strcat e my_strcmp: o header só declara, não define.

Não é isso. Sem my_string.o, o linker não encontra as definições das funções declaradas no header. O erro acontece na ligação, não na compilação de main.c, e o executável não é gerado.

main.c não contém nenhum protótipo: a declaração das funções vem do header, e a definição, do arquivo objeto ligado no fim. O exemplo compila sem nenhum aviso com -Wall.

#include <stdlib.h>
#include <math.h>

int main()
{
    // Create a circle with center (0, 0) and radius 5
    Circle *my_circle = create_circle(0, 0, 5);

    // Create a point with coordinates (2, 1)
    Point2D *my_point = create_point(2, 1);

    // Check if the point is inside the circle

    {
        printf("The point is inside the circle.\n");
    }
    else

        printf("The point is outside the circle.\n");
    }

    // Deallocate memory
    free_circle(my_circle);
    free_point(my_point);

    return 0;
}

Como funcionam o TAD Ponto e o TAD Círculo

O TAD Ponto (point2d.h) exporta create_point, euclidean_distance e free_point. A struct point2d é definida só em point2d.c; o cliente recebe apenas Point2D *, sem acesso aos campos x e y.

O TAD Círculo (circle.h) inclui point2d.h, porque sua operação is_point_inside_circle recebe um ponto. Internamente, a struct circle guarda um Point2D * para o centro e um double para o raio. create_circle cria o centro com create_point, e free_circle libera esse centro antes da própria struct.

O programa de teste usa somente os headers. Ele cria um círculo e um ponto, consulta se o ponto está dentro, e libera os dois blocos que criou.

Operações conceituais, não implementadas no exemplo. O TAD Ponto também prevê acessa e atribui, e o TAD Círculo prevê area. O projeto não implementa nenhuma dessas três: não há função para ler ou alterar as coordenadas do ponto, nem para calcular a área do círculo. Elas não aparecem na simulação abaixo.

#include "point2d.h"
#include <math.h>
#include <stdio.h>
#include <stdlib.h>

// Define a Point2D structure
struct point2d {
  double x;
  double y;
};

// Function to calculate the Euclidean distance between two points
double euclidean_distance(Point2D *point1, Point2D *point2) {
  double dx = point1->x - point2->x;
  double dy = point1->y - point2->y;
  return sqrt(dx * dx + dy * dy);
}

// Function to create a new Point2D
Point2D *create_point(double x, double y) {
  Point2D *new_point = (Point2D *)malloc(sizeof(Point2D));
  if (new_point == NULL) {
    perror("Failed to allocate memory for Point2D");
    exit(EXIT_FAILURE);
  }
  new_point->x = x;
  new_point->y = y;
  return new_point;
}

// Function to deallocate a Point2D
void free_point(Point2D *point)
{
    free(point);
}

02_circle/src/circle.c

#include "circle.h"
#include <stdio.h>
#include <stdlib.h>

struct circle
{
    Point2D *center;
    double radius;
};

// Function to create a new Circle
Circle *create_circle(double center_x, double center_y, double radius)
{
    Circle *new_circle = (Circle *)malloc(sizeof(Circle));
    if (new_circle == NULL)
    {
        perror("Failed to allocate memory for Circle");
        exit(EXIT_FAILURE);
    }
    new_circle->center = create_point(center_x, center_y);
    new_circle->radius = radius;
    return new_circle;
}

// Function to check if a point is inside a circle
int is_point_inside_circle(Point2D *point, Circle *circle)
{
    double distance = euclidean_distance(point, circle->center);

    // If the distance is less than the radius, the point is inside the circle
    if (distance < circle->radius)
    {
        return 1; // Inside
    }
    else
    {
        return 0; // Outside
    }
}

// Function to deallocate a Circle
void free_circle(Circle *circle)
{
    free_point(circle->center);
    free(circle);
}
Pergunta de checagem

O que aconteceria se create_circle recebesse raio 2, em vez de 5, mantendo o ponto (2, 1)?

  • AO ponto continuaria dentro, porque suas coordenadas não mudaram.
  • BO ponto passaria a ficar fora, porque a distância até o centro, cerca de 2,236, não é menor que 2.
  • CO programa não compilaria, porque o raio precisa ser um número inteiro.
  • DA consulta passaria a usar o raio para calcular a área, e a saída não mudaria.

Certo! A comparação é distance < radius. Com raio 2, a distância de aproximadamente 2,236 não é menor, então a função devolve 0 e a saída seria "outside".

Não é isso. A consulta compara a distância até o centro com o raio. Com raio 2, a distância de cerca de 2,236 não é menor, e o ponto passa a ficar fora do círculo.

O cliente nunca acessa circle->center nem circle->radius: usa só as funções exportadas pelos headers. O exemplo compila sem nenhum aviso com -Wall e liga a biblioteca matemática por -lm.

#include <stdio.h>
#include "matrix.h"

int main() {
    // Create a 3x4 matrix
    Matrix *mat = matrix_create(3, 4);

    // Fill it: element (i, j) receives the value i * 10 + j
    for (int i = 0; i < matrix_rows(mat); i++) {
        for (int j = 0; j < matrix_cols(mat); j++) {
            matrix_set(mat, i, j, i * 10 + j);
        }
    }

    // Print using only the ADT interface; this code never touches
    // the fields of struct matrix directly.
    printf("Matrix %d x %d:\n", matrix_rows(mat), matrix_cols(mat));
    for (int i = 0; i < matrix_rows(mat); i++) {
        for (int j = 0; j < matrix_cols(mat); j++) {
            printf("%5.1f ", matrix_get(mat, i, j));
        }
        printf("\n");
    }

    matrix_free(mat);

    return 0;
}

Como funciona o TAD Matriz

matrix.h é a interface. Declara o tipo opaco Matrix e as seis operações: matrix_create, matrix_free, matrix_get, matrix_set, matrix_rows e matrix_cols. Não há nenhum campo visível para o cliente.

matrix.c é a implementação. A struct guarda rows, cols e um ponteiro data para um bloco contíguo de floats, alocado com calloc, então todos os elementos começam em 0. O elemento (i, j) fica em data[i * cols + j].

test_matrix.c cria uma matriz 3 × 4, preenche cada elemento com i * 10 + j, imprime a matriz e libera a memória. Ele usa somente as funções do header, e por isso a implementação pode trocar o vetor simples por vetor de ponteiros sem mudança neste arquivo.

03_matrix/src/matrix.c

#include "matrix.h"
#include <stdio.h>
#include <stdlib.h>

// Implementation with a flat array: all elements live in one contiguous
// block, and element (i, j) is stored at data[i * cols + j].
// This is an internal detail of the module; clients never need to know it.
struct matrix {
    int rows;
    int cols;
    float *data;
};

Matrix *matrix_create(int m, int n) {
    Matrix *mat = (Matrix *)malloc(sizeof(Matrix));
    if (mat == NULL) {
        perror("Failed to allocate memory for Matrix");
        exit(EXIT_FAILURE);
    }

    mat->rows = m;
    mat->cols = n;
    mat->data = (float *)calloc(m * n, sizeof(float));
    if (mat->data == NULL) {
        perror("Failed to allocate memory for Matrix elements");
        exit(EXIT_FAILURE);
    }

    return mat;
}

void matrix_free(Matrix *mat) {
    free(mat->data);
    free(mat);
}

float matrix_get(Matrix *mat, int i, int j) {
    return mat->data[i * mat->cols + j];
}

void matrix_set(Matrix *mat, int i, int j, float v) {
    mat->data[i * mat->cols + j] = v;
}

int matrix_rows(Matrix *mat) {
    return mat->rows;
}

int matrix_cols(Matrix *mat) {
    return mat->cols;
}
Pergunta de checagem

Por que test_matrix.c não precisaria mudar se a implementação trocasse o vetor simples por um vetor de ponteiros?

  • APorque o compilador converte automaticamente float ** em float * em cada chamada.
  • BPorque o programa só imprime valores inteiros, e a representação interna não afeta a saída.
  • CPorque o programa usa só as funções de matrix.h e não acessa os campos da struct, então a mudança fica restrita a matrix.c.
  • DPorque test_matrix.c inclui o arquivo matrix.c diretamente, e nele a mudança é invisível.

Certo! O cliente depende só do contrato. Como ele não toca em rows, cols nem em data, a forma de armazenamento fica restrita a matrix.c.

Não é isso. O ponto é o encapsulamento: o programa de teste só chama matrix_create, matrix_set, matrix_get e as demais funções do header. A mudança de armazenamento fica dentro de matrix.c.

test_matrix.c nunca lê os campos da struct: usa só as seis funções de matrix.h. O exemplo compila sem nenhum aviso com -Wall, e a saída é a mesma que o material de referência descreve para uma matriz 3 × 4 preenchida com i × 10 + j.
Para lembrar. Um módulo tem uma interface (.h) e uma implementação (.c) compiladas em separado. Um TAD esconde a struct atrás de ponteiros opacos, e o cliente depende só das operações exportadas, não da forma como o tipo é armazenado.
