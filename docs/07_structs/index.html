Tipos estruturados

Tipos estruturados em C

Estas são as notas da nona aula: como agrupar valores de tipos diferentes numa única unidade com struct, como manipular essas structs por ponteiro e alocá-las dinamicamente, como batizar um tipo novo com typedef, como aninhar uma struct dentro de outra e organizá-las em vetores — e os tipos union e enum, dois primos de struct com papéis mais específicos. Os exemplos interativos logo abaixo colocam parte dessa teoria em prática, passo a passo.

Tipos estruturados

Até aqui, cada variável deste curso guardava um valor de um único tipo — um int, um float, um vetor de um desses. Muitos problemas, porém, giram em torno de uma entidade composta por vários valores relacionados: um ponto no plano tem uma coordenada x e uma y; um aluno tem nome, matrícula e nota. Representar cada um desses campos como uma variável solta funciona, mas obriga o programador a carregar manualmente o vínculo entre eles — passar três parâmetros para toda função que lida com "o aluno", por exemplo, em vez de um só. A struct resolve exatamente essa lacuna: um novo tipo composto, definido pelo próprio programador, que agrupa vários campos (de tipos iguais ou diferentes) sob um único nome.

Estruturas

A sintaxe básica declara a "forma" da struct — seus campos e os tipos de cada um — sem ainda criar nenhuma variável: 

struct point2d
{
    float x;
    float y;
};

point2d aqui é o nome da struct (a "etiqueta", ou tag), não o nome de uma variável — struct point2d point; é que declara de fato uma variável chamada point, desse tipo. Cada campo é acessado com o operador ponto: point.x = 3;, point.y = 4;. É esse o padrão que o exemplo Ponto 2D: variável ponteiro usa para ler as coordenadas diretamente em main, antes de qualquer ponteiro entrar em cena.

Ponteiros para estruturas

Assim como qualquer outra variável, uma struct pode ter seu endereço guardado num ponteiro: struct point2d *point_ptr = &point;. A diferença prática está no operador de acesso aos campos: em vez do ponto (.), usado quando se tem a struct em si, um ponteiro para struct usa a seta (->) — point_ptr->x é só um atalho para (*point_ptr).x (primeiro desreferencia o ponteiro, depois acessa o campo), mas escrito de um jeito muito mais legível. É essa seta que aparece em todos os cinco exemplos deste módulo, sempre que uma função recebe uma struct por ponteiro.

Passagem de estruturas para funções

Passar uma struct para uma função por valor (só struct point2d p como parâmetro, sem *) copia todos os seus campos para dentro da função — qualquer alteração feita lá dentro não é vista por quem chamou, exatamente como acontece com um int comum. Por isso o padrão adotado em todos os exemplos deste módulo é passar structs por ponteiro: a função recebe o endereço da struct original (struct point2d *point) e manipula os campos diretamente através dele, sem cópia. É o que os exemplos Ponto 2D via ponteiro e Ponto 2D: variável ponteiro ilustram lado a lado: no primeiro, o próprio parâmetro da função já chega como ponteiro (read_point(&point)); no segundo, uma variável ponteiro comum (point_ptr) é declarada à parte, apontando para uma struct já existente, e usada para alterar seus campos fora de qualquer função. Um detalhe que aparece em Ponto 2D via ponteiro: quando a função só precisa ler os campos, sem alterá-los (como print_point), o parâmetro pode ser declarado const struct point2d *point — o const promete ao compilador (que passa a barrar qualquer tentativa de escrita) que a struct apontada não será modificada ali dentro.

Alocação dinâmica de estruturas

Uma struct também pode ser alocada dinamicamente, do mesmo jeito que um vetor: struct point2d *point = malloc(sizeof(struct point2d));. O padrão de sempre se aplica sem surpresas — sizeof calcula o tamanho exato da struct (a soma dos tamanhos de seus campos, com algum ajuste de alinhamento que o compilador cuida sozinho), malloc devolve o endereço do bloco recém-reservado no heap, e é preciso verificar se o retorno não foi NULL antes de usá-lo. A diferença mais visível para quem só viu structs na pilha: como o exemplo Ponto 2D alocado dinamicamente mostra, a variável point já é um ponteiro desde a declaração — não existe mais nenhuma struct "solta" para tirar o endereço com &; as funções recebem point diretamente, e o bloco só é devolvido ao heap com free(point); ao final.

Definição de novos tipos

Escrever struct point2d por extenso toda vez que se quer declarar uma variável, um parâmetro ou um retorno de função é repetitivo. O typedef resolve isso criando um apelido para o tipo: 

typedef struct point2d Point2D;

A partir daí, Point2D passa a significar exatamente a mesma coisa que struct point2d, mas sem precisar repetir a palavra struct: Point2D *point = malloc(sizeof(Point2D)); é o exemplo Distância entre pontos (typedef) aplicando essa troca. É comum, inclusive, pular a etapa de nomear a struct separadamente e combinar as duas declarações numa só, com uma struct anônima (sem tag própria) logo seguida do apelido — é o padrão que o exemplo Círculo (structs aninhadas) usa tanto para Point2D quanto para Circle: 

typedef struct
{
    double x;
    double y;
} Point2D;

Aninhamento de estruturas

Um campo de uma struct pode, ele próprio, ser outra struct — ou, mais comumente quando a struct interna também é alocada dinamicamente, um ponteiro para outra struct. É o padrão do exemplo Círculo (structs aninhadas): um Circle guarda um Point2D *center (o centro) e um double radius — para chegar até as coordenadas do centro a partir de um Circle *circle, é preciso encadear dois acessos: circle->center->x primeiro segue a seta até o Point2D apontado por center, depois acessa o campo x dele. Esse aninhamento também muda a ordem da liberação de memória: como center foi alocado separadamente (dentro de create_circle, que chama create_point para isso), liberar um Circle exige liberar primeiro o Point2D apontado por center, e só depois o próprio Circle — na ordem inversa, perderia o único ponteiro que leva até o centro, vazando aquele bloco de memória.

Vetores de estruturas

Como qualquer outro tipo, uma struct pode ser o tipo dos elementos de um vetor: Point2D pontos[N]; declara N pontos em sequência, cada um acessado normalmente por índice — pontos[i].x. É uma forma natural de representar uma coleção de entidades do mesmo tipo, como os vértices de um polígono: em vez de um vetor de xs e um vetor separado de ys (que o programador precisaria manter sincronizados manualmente), um único vetor de Point2D já mantém cada par de coordenadas junto, na posição correspondente ao vértice.

O exemplo Vetor de vértices, union e enum deste módulo aplica exatamente essa técnica, sem ainda calcular a área: um vetor de 4 Point2D guarda os vértices de um polígono retangular, e um laço percorre o vetor por índice (poligono[i].x, poligono[i].y) para imprimir cada vértice — a mesma organização da Figura 9.1 acima, só sem a soma de trapézios.

Vetores de ponteiros para estruturas

Quando cada struct é alocada dinamicamente (em vez de viver inteira dentro do vetor), o vetor passa a guardar ponteiros para essas structs, não as structs em si: Point2D *pontos[N]; — mesma ideia já vista no módulo de cadeias de caracteres para um vetor de strings (char *nomes[N];), agora aplicada a structs. Cada posição pontos[i] aponta para um bloco independente do heap, o que permite, por exemplo, alocar só os pontos que de fato serão usados, ou compartilhar a mesma struct entre mais de um vetor sem duplicar seu conteúdo.

Tipo Union

Uma union se declara com uma sintaxe quase idêntica à de uma struct, mas o significado é bem diferente: enquanto uma struct reserva espaço separado para cada campo (todos coexistindo ao mesmo tempo), uma union reserva um único espaço de memória, do tamanho do maior de seus campos, e todos os campos compartilham esse mesmo espaço — escrever num campo sobrescreve o que estava guardado em qualquer outro. 

union valor
{
    int i;
    float f;
};

union valor v;
v.i = 10;      // grava um int nos 4 bytes da union
v.f = 3.14;    // sobrescreve os mesmos 4 bytes com um float
                 // a essa altura, v.i já não vale mais 10

Uma union é útil quando se sabe que, em cada instante, só um dos campos estará "ativo" de verdade — por exemplo, para economizar memória guardando um valor que pode ser ou um int ou um float, nunca os dois ao mesmo tempo, sem precisar do espaço somado dos dois tipos como uma struct exigiria.

O exemplo Vetor de vértices, union e enum traz essa ideia em código real: uma union Valor com campos como_inteiro (int) e como_real (float). Depois de v.como_real = 3.14f;, o próprio programa imprime sizeof(Valor) — 4 bytes, não os 4+4=8 que uma struct equivalente ocuparia, já que os dois campos compartilham o mesmo espaço.

Tipo Enum

Um enum (enumeração) define um novo tipo cujos valores possíveis são uma lista nomeada de constantes — útil para representar um conjunto pequeno e fixo de opções (um dia da semana, um estado de um jogo, uma cor) de um jeito muito mais legível do que "o código 0 significa segunda-feira, o código 1 significa terça-feira...": 

enum dia_semana { DOM, SEG, TER, QUA, QUI, SEX, SAB };

enum dia_semana hoje = TER;
if (hoje == TER)
    printf("É terça-feira!\n");

Por baixo, cada nome do enum é só uma constante inteira — por padrão, DOM vale 0, SEG vale 1, e assim por diante, na ordem em que aparecem — mas usar o nome (TER) em vez do número (2) deixa o código muito mais claro sobre o que ele representa, sem perder a eficiência de comparar e armazenar um inteiro simples.

O exemplo Vetor de vértices, union e enum combina os dois tipos desta seção e da anterior: um enum TipoValor (TIPO_INTEIRO, TIPO_REAL) identifica qual campo da union Valor está em uso naquele momento — um padrão comum, já que a union sozinha não guarda essa informação (os bytes compartilhados não dizem se foram escritos como int ou como float).

Ponto 2D via ponteiro

#include <stdio.h>

struct point2d
{
    float x;
    float y;
};

void read_point(struct point2d *point)
{
    printf("Enter the x-coordinate: ");
    scanf("%f", &(point->x));

    printf("Enter the y-coordinate: ");
    scanf("%f", &(point->y));
}

void print_point(const struct point2d *point)
{
    printf("The 2D point has the following coordinates:\n");
    printf("x = %.2f\n", point->x);
    printf("y = %.2f\n", point->y);
}

int main()
{
    struct point2d point;
    read_point(&point);
    print_point(&point);
    return 0;
}

Struct como parâmetro, sempre por ponteiro

point é declarada em main, na pilha, e seu endereço (&point) é o que de fato viaja para read_point e print_point — dentro de cada função, o parâmetro point é um ponteiro, e o acesso aos campos usa a seta (point->x), não o ponto. Como print_point só lê os campos, sem alterá-los, o parâmetro é declarado const: uma promessa ao compilador (e a quem lê o código) de que essa função não modifica a struct apontada.

Pergunta de checagem

read_point recebe point como struct point2d *point (ponteiro). Se a função fosse reescrita recebendo struct point2d point (por valor, sem ponteiro) — trocando toda ocorrência de point-> por point. — o que aconteceria com os valores lidos do teclado?

  • Apoint.x e point.y seriam gravados em main também, já que scanf sempre altera a variável original.
  • Bpoint.x e point.y seriam gravados só na cópia local dentro de read_point; a struct point em main continuaria com valores indefinidos.
  • CO programa não compilaria, pois scanf exige sempre um ponteiro como parâmetro de função.
  • Dread_point passaria a exigir dois parâmetros em vez de um.

Certo! Passar a struct por valor copia seus campos para dentro da função — scanf escreveria nessa cópia local, que desaparece quando read_point retorna. A struct point de main nunca seria tocada, ficando com lixo de memória. É exatamente por isso que o exemplo passa a struct por ponteiro.

Não é isso. Por valor, a struct inteira é copiada para dentro da função — scanf escreveria só nessa cópia local, que some ao fim de read_point. A point de main ficaria com valores indefinidos, sem nunca ser lida de verdade.

Ponto 2D: variável ponteiro

#include <stdio.h>

struct point2d
{
    float x;
    float y;
};

void print_point(struct point2d *point_ptr)
{
    printf("x=%.2f y=%.2f\n", point_ptr->x, point_ptr->y);
}

int main()
{
    struct point2d point;
    printf("Enter the x and y coordinates in a single line: ");
    scanf("%f %f", &point.x, &point.y);
    print_point(&point);

    struct point2d *point_ptr = &point;
    point_ptr->x += 1.0;
    point_ptr->y += 2.0;
    printf("After manipulation, the 2D point has the following coordinates: (%.2f, %.2f)\n", point_ptr->x, point_ptr->y);
    return 0;
}

Um ponteiro não precisa vir de um parâmetro

Diferente do exemplo anterior, aqui point_ptr não é parâmetro de nenhuma função — é uma variável ponteiro comum, declarada em main, apontando para uma struct que já existia (point). A partir daí, alterar um campo através de point_ptr->x altera point de verdade, porque os dois nomes levam ao mesmo endereço de memória — point.x e point_ptr->x são, neste programa, duas formas de acessar exatamente o mesmo float.

Pergunta de checagem

Suponha que o código também declarasse struct point2d outro_point; e, logo depois de point_ptr = &point;, executasse point_ptr = &outro_point;. A partir dali, o que point_ptr->x += 1.0; passaria a alterar?

  • Aoutro_point, não mais point — point ficaria intocada por point_ptr dali em diante.
  • Bpoint e outro_point ao mesmo tempo, já que point_ptr já apontou para as duas em algum momento.
  • CO programa não compilaria, pois um ponteiro só pode receber um endereço uma única vez.
  • Dpoint e outro_point passariam a ocupar o mesmo endereço de memória.

Certo! Um ponteiro guarda um único endereço por vez — reatribuir point_ptr só muda para onde ele aponta agora, sem nenhum vínculo remanescente com o endereço anterior. Depois da reatribuição, point_ptr->x lê e escreve só em outro_point.

Não é isso. A resposta certa é: só outro_point passa a ser alterada. Um ponteiro guarda um único endereço por vez — reatribuir point_ptr descarta o vínculo anterior com point, sem afetar seu endereço de memória real.

#include <stdio.h>
#include <stdlib.h>

struct point2d
{
    float x;
    float y;
};

void read_point(struct point2d *point)
{
    printf("Enter the x-coordinate: ");
    scanf("%f", &(point->x));
    printf("Enter the y-coordinate: ");
    scanf("%f", &(point->y));
}

void print_point(const struct point2d *point)
{
    printf("The 2D point has the following coordinates:\n");
    printf("x = %.2f\n", point->x);
    printf("y = %.2f\n", point->y);
}

int main()
{
    struct point2d *point;
    point = (struct point2d *)malloc(sizeof(struct point2d));
    if (point == NULL)
    {
        printf("Memory allocation failed.\n");
        return 1;
    }
    read_point(point);
    print_point(point);
    free(point);
    return 0;
}

Nenhuma struct na pilha — só o ponteiro

A diferença central para os dois exemplos anteriores: struct point2d *point; declara apenas uma variável ponteiro, sem nenhuma struct correspondente ainda existindo em lugar nenhum. É só depois de malloc(sizeof(struct point2d)) que um bloco de memória (no heap, do tamanho exato de dois float) passa a existir, e point passa a apontar para ele. Como point já é um endereço, as chamadas read_point(point) e print_point(point) não usam & — diferente do primeiro exemplo, onde era preciso tirar o endereço de uma struct da pilha.

Depois de free(point);, a variável point continua existindo e ainda guarda o mesmo endereço, mas esse endereço não pertence mais ao programa — usá-lo (por exemplo, point->x depois do free) seria um use-after-free, o mesmo bug já visto no módulo de alocação dinâmica, agora aplicado a uma struct em vez de um vetor.
Pergunta de checagem

O callout menciona que ler point->x depois de free(point); seria um use-after-free. Por que esse tipo de acesso nem sempre falha de forma óbvia (um crash imediato), tornando o bug particularmente perigoso?

  • APorque free() não libera a memória de verdade, só marca um sinalizador interno que malloc ignora depois.
  • BPorque o sistema operacional impede qualquer leitura de memória liberada, sempre gerando um erro claro e imediato.
  • CPorque o bloco liberado pode continuar com os bytes antigos por um tempo, até ser reaproveitado por outra alocação — o programa às vezes lê valores que ainda parecem corretos, mascarando o bug.
  • DPorque o compilador substitui automaticamente qualquer acesso pós-free por zero, sem avisar.

Certo! free() devolve o bloco ao alocador, mas não apaga o conteúdo na hora — os bytes antigos costumam continuar lá até alguma alocação futura reutilizar aquele espaço. Isso faz um use-after-free às vezes "funcionar por acaso", o que é exatamente o que o torna perigoso: o bug pode passar despercebido em testes e só aparecer depois, de forma imprevisível.

Não é isso. O motivo real é que o bloco liberado costuma manter os bytes antigos por um tempo, até ser reaproveitado por outra alocação — o programa pode ler valores que ainda parecem corretos, sem nenhum erro visível, o que torna esse bug traiçoeiro de detectar.

Distância entre pontos (typedef)

#include <stdio.h>
#include <stdlib.h>
#include <math.h>

struct point2d
{
    float x;
    float y;
};

typedef struct point2d Point2D;

Point2D *create_point()
{
    Point2D *point = (Point2D *)malloc(sizeof(Point2D));
    if (point == NULL)
    {
        printf("Memory allocation failed.\n");
        exit(1);
    }
    return point;
}

void read_point(Point2D *point)
{
    printf("Enter the x-coordinate: ");
    scanf("%f", &(point->x));
    printf("Enter the y-coordinate: ");
    scanf("%f", &(point->y));
}

void print_point(const Point2D *point)
{
    printf("Point: (%.2f, %.2f)\n", point->x, point->y);
}

float euclidean_distance(const Point2D *point1, const Point2D *point2)
{
    float dx = point2->x - point1->x;
    float dy = point2->y - point1->y;
    return sqrt(dx * dx + dy * dy);
}

void free_point(Point2D *point)
{
    free(point);
}

int main()
{
    Point2D *point1 = create_point();
    Point2D *point2 = create_point();

    printf("Enter the coordinates of the first point:\n");
    read_point(point1);
    printf("Enter the coordinates of the second point:\n");
    read_point(point2);

    printf("Coordinates of the first point:\n");
    print_point(point1);
    printf("Coordinates of the second point:\n");
    print_point(point2);

    float distance = euclidean_distance(point1, point2);
    printf("Euclidean distance between the two points: %.2f\n", distance);

    free_point(point1);
    free_point(point2);
    return 0;
}

Point2D, não struct point2d

typedef struct point2d Point2D; cria o apelido usado no resto do arquivo — a partir dali, Point2D e struct point2d significam exatamente o mesmo tipo, mas só o apelido aparece no código. Repare também o padrão create_point/free_point: uma função de "fábrica" que aloca e devolve um ponteiro pronto para uso, espelhada por uma função que devolve a memória — o mesmo padrão do exemplo anterior, só que encapsulado em funções próprias. euclidean_distance mostra ainda uma função recebendo duas structs por ponteiro, não uma só.

Pergunta de checagem

euclidean_distance recebe point1 e point2 como const Point2D *. O que exatamente o compilador passa a impedir, dentro dessa função, por causa do const?

  • ARetornar um float como resultado da função.
  • BChamar create_point() em qualquer lugar do arquivo.
  • CLer os campos x e y de point1 e point2.
  • DAtribuir um novo valor a point1->x ou point2->y dentro da função.

Certo! const promete ao compilador que a função não vai escrever nos campos apontados — qualquer tentativa de atribuição, como point1->x = 0;, vira erro de compilação. Ler os campos continua livre; a restrição é só sobre escrita.

Não é isso. A resposta certa é: atribuir um novo valor a um campo de point1 ou point2 dentro da função. const não impede leitura, nem chamadas a outras funções — só barra escrita nos dados apontados.

Círculo (structs aninhadas)

#include <stdio.h>
#include <stdlib.h>
#include <math.h>

typedef struct
{
    double x;
    double y;
} Point2D;

typedef struct
{
    Point2D *center;
    double radius;
} Circle;

double euclidean_distance(Point2D *point1, Point2D *point2)
{
    double dx = point1->x - point2->x;
    double dy = point1->y - point2->y;
    return sqrt(dx * dx + dy * dy);
}

Point2D *create_point(double x, double y)
{
    Point2D *new_point = (Point2D *)malloc(sizeof(Point2D));
    if (new_point == NULL)
    {
        perror("Failed to allocate memory for Point2D");
        exit(EXIT_FAILURE);
    }
    new_point->x = x;
    new_point->y = y;
    return new_point;
}

Circle *create_circle(double center_x, double center_y, double radius)
{
    Circle *new_circle = (Circle *)malloc(sizeof(Circle));
    if (new_circle == NULL)
    {
        perror("Failed to allocate memory for Circle");
        exit(EXIT_FAILURE);
    }
    new_circle->center = create_point(center_x, center_y);
    new_circle->radius = radius;
    return new_circle;
}

int is_point_inside_circle(Point2D *point, Circle *circle)
{
    double distance = euclidean_distance(point, circle->center);
    if (distance < circle->radius)
        return 1;
    else
        return 0;
}

void free_point(Point2D *point)
{
    free(point);
}

void free_circle(Circle *circle)
{
    free_point(circle->center);
    free(circle);
}

int main()
{
    Circle *my_circle = create_circle(0, 0, 5);
    Point2D *my_point = create_point(2, 1);

    if (is_point_inside_circle(my_point, my_circle))
        printf("The point is inside the circle.\n");
    else
        printf("The point is outside the circle.\n");

    free_circle(my_circle);
    free_point(my_point);
    return 0;
}

Uma struct dentro da outra

Circle não guarda as coordenadas do centro diretamente — guarda um Point2D *center, um ponteiro para uma struct alocada separadamente. Chegar até x do centro a partir de um Circle *circle exige duas setas em sequência: circle->center primeiro leva até o Point2D, e só então ->x acessa a coordenada. create_circle monta essa estrutura aninhada chamando create_point internamente; free_circle desfaz na ordem inversa, liberando center antes do próprio circle.

Vetor de vértices, union e enum

#include <stdio.h>

typedef struct
{
    float x;
    float y;
} Point2D;

typedef enum
{
    TIPO_INTEIRO,
    TIPO_REAL
} TipoValor;

typedef union
{
    int como_inteiro;
    float como_real;
} Valor;

int main()
{
    Point2D poligono[4] = {
        {0.0, 0.0},
        {4.0, 0.0},
        {4.0, 3.0},
        {0.0, 3.0}
    };

    printf("Vertices do poligono:\n");
    for (int i = 0; i < 4; i++)
    {
        printf("  p%d = (%.1f, %.1f)\n", i, poligono[i].x, poligono[i].y);
    }

    TipoValor tipo = TIPO_REAL;
    Valor v;
    v.como_real = 3.14f;

    printf("\n");
    if (tipo == TIPO_INTEIRO)
    {
        printf("Valor inteiro: %d\n", v.como_inteiro);
    }
    else
    {
        printf("Valor real: %.2f\n", v.como_real);
    }
    printf("Tamanho da union Valor: %lu bytes\n", sizeof(Valor));

    return 0;
}

Vetor de Point2D, depois union e enum juntos

A primeira metade fecha a lacuna dos "Vetores de estruturas": Point2D poligono[4] é um vetor comum, já inicializado com as coordenadas dos quatro vértices de um retângulo, percorrido por índice num for — a mesma organização da Figura 9.1 das notas, sem a soma de trapézios.

A segunda metade demonstra union e enum juntos: o enum TipoValor indica qual campo da union Valor está em uso — tipo = TIPO_REAL diz que o programa deve ler v.como_real, não v.como_inteiro. Como os dois campos da union compartilham o mesmo espaço de memória, escrever em v.como_real não deixa v.como_inteiro com nenhum valor separado — só os mesmos bytes, reinterpretados como outro tipo.

Pergunta de checagem

O programa imprime que sizeof(Valor) vale 4 bytes. Se Valor fosse declarada como struct em vez de union — mantendo os mesmos dois campos, como_inteiro e como_real — qual seria o valor mais provável de sizeof(Valor), e por quê?

  • AAinda 4 bytes — struct e union sempre ocupam o mesmo espaço, só muda a forma de acessar os campos.
  • B0 bytes — sizeof não funciona em structs com campos de tipos diferentes.
  • C8 bytes — uma struct reserva espaço separado para cada campo (4 + 4), enquanto a union reserva um único espaço do tamanho do maior campo.
  • DDepende do valor atribuído em tempo de execução — não dá para saber sem rodar o programa.

Certo! Numa struct, como_inteiro e como_real teriam endereços diferentes, cada um com seus próprios 4 bytes, coexistindo ao mesmo tempo — pelo menos 8 bytes ao todo. Na union, os dois campos apontam para o mesmo endereço, por isso sizeof(Valor) é 4, não 8: o tamanho do maior campo, nunca a soma deles.

Não é isso. A resposta certa é 8 bytes. Diferente da union (onde os campos compartilham o mesmo espaço, daí os 4 bytes), uma struct reserva um espaço separado para cada campo — como_inteiro e como_real, cada um com seus 4 bytes, coexistindo ao mesmo tempo.
